# v0.2 手机投屏

v0.1 先在手机和电脑浏览器上实现网页播放。v0.2 在家庭局域网内实现手机发起投屏和控制播放，电视负责接收。交付至少用一组实际手机和电视或电视盒子验收。设备资料、网页播放和项目里程碑见 [网页播放 MVP](web-mvp.md) 与 [项目计划](plan.md)。

## 确认设备与协议

1. 记录手机型号、系统与浏览器版本，以及电视或盒子型号、系统版本和已启用的接收功能。确认设备可在同一家庭网络内发现和连接。
2. 按目标设备选候选路线。使用可以重复访问的测试媒体，依次验证发现目标、开始实际视频播放、从指定位置开播、暂停后跳转、换到下一集和结束投屏。
3. 依据实机结果选择支持路线。候选方案若卡在核心操作，记录设备、浏览器、媒体 URL、出错步骤和实际表现，优先验证当前设备可用的另一条路线。没有成功验证的组合保持待验证或记录为阻塞。

| 设备和浏览器条件 | 验证方式 | 需要确认的行为 |
| --- | --- | --- |
| 目标手机用 iPhone Safari，电视或盒子支持 AirPlay | 用 Safari 的原生视频元素触发系统设备选择器，先验证同源直连 MP4。若采用 HLS，优先走 Safari 的原生 HLS。 | 以电视画面确认实际视频投送。验证视频元素的播放、暂停、时间和无线播放状态是否可用，以及换集后原生路由是否保留。 |
| 电视或盒子支持 Google Cast，目标手机浏览器可以运行 Web Sender | 用 Google Cast Web Sender 验证接收端会话。常规 MP4 或 HLS 先试 Default Media Web Receiver。 | 验证浏览器能发现设备，接收端能加载媒体，手机能订阅播放状态并控制接收端。 |
| 现有设备协议受限，电视浏览器可访问 MediaHub | 仅在家庭使用方式允许电视先打开接收页时，验证电视页与手机扫码或短码配对。 | 验证电视浏览器解码、自动播放、断线和实机控制。手机仍负责选片与控制，接收页只承担电视播放。 |
| 现有设备仅支持 DLNA | 验证是否已有可用的本地控制端。若需要局域网桥接，先确认常驻设备与维护成本。 | 浏览器通常缺少直接执行 DLNA 发现和控制的接口。桥接方案须单独验证后再确定是否采用。 |

参考 [Apple AirPlay 使用说明](https://support.apple.com/en-us/102661)、[WebKit 关于 AirPlay 和媒体源的说明](https://webkit.org/blog/15036/how-to-use-media-source-extensions-with-airplay/) 与 [Google Cast Web Sender](https://developers.google.com/cast/docs/web_sender)。

## 网页播放器与媒体

- v0.1 播放器对上层提供当前 `contentId`、绝对 `mediaUrl`、以秒计的 `currentTime` 和播放状态。切换影片或剧集时，整组数据指向新内容。投屏接入与会话控制放在 v0.2。
- `public/media/` 存放家庭测试媒体并加入 Git 忽略规则，经网页服务映射到 `/media/`。v0.2 从局域网中的另一台设备确认服务地址可访问，例如服务器的局域网 IP 或家庭域名。对需要接收端拉流的路线，提交电视可访问的绝对 URL，随后在电视上验证。手机本机的 `localhost`、`blob:` 地址和依赖手机浏览器登录状态的请求无法作为通用接收端地址。
- 先验证一份实际编码为 H.264/AAC 的 MP4。走 MP4 时检查范围请求和拖动。若采用 HLS，逐项确认清单、分片、相关跨域配置和编解码兼容。换集验收需要两条媒体地址。接收端的网络、证书和解码行为以设备结果为准。
- Google Cast Web Sender 的发送页面按受信任 HTTPS 配置。接收端媒体地址优先使用双方都信任的 HTTPS，验证证书链、主机名和媒体资源是否可达，以及是否触发跨域或混合内容限制。AirPlay 从 Safari 原生媒体路径实测，播放方案若使用 MSE 或 `blob:`，还需要验证接收端可用的直连媒体地址。家庭 HTTP 页面能开播时，仍需针对选定投屏路线验证。参考 [Google Cast Web Sender 集成指南](https://developers.google.com/cast/docs/web_sender/integrate) 和 [支持的媒体格式](https://developers.google.com/cast/docs/media)。

## 会话行为

| 操作 | 实现与验收要求 |
| --- | --- |
| 发起与交接 | 从当前影片或剧集、播放位置和暂停或播放状态开始。Cast 或自建接收页确认电视接管后，再停止手机本地输出。AirPlay 对原生视频元素沿用同一套控制，让系统切换输出。手机界面区分等待、已连接和失败，以接收端或原生媒体事件确认结果。 |
| 播放和暂停 | 控制当前投屏会话。电视执行后更新手机可确认的状态。接收端拒绝指令时显示失败。 |
| 跳转和进度 | 手机能在电视上跳到指定时间，以实际接收端位置或确认可用的原生事件更新进度。协议只能提供部分信息时，显示可确认的位置或省略不可用的实时进度。 |
| 换集 | 将下一集交给同一台电视，从新集的起始位置播放，手机同步更新当前剧集。原生路由如果在换集时中断，按实机行为记录阻塞并评估替代路线。 |
| 停止 | 用户从手机停止投屏，确认电视结束本次播放、手机退出投屏状态。能取得最近确认的位置时从该处保留当前剧集，供手机继续播放。协议无法提供可靠位置时保留已知位置，界面避免声称已同步。 |
| 失败和断开 | 区分找不到设备、连接失败、媒体加载失败和播放中断线。保持手机可以继续操作，提供重试或回到手机播放的入口。指令失败时保留最后确认的会话状态。 |

Cast 以 Web Sender 会话和媒体状态为准。AirPlay 以系统选择器、视频元素和 WebKit 可用事件为准。设备发现、会话结束或实时进度若只能用系统控件、人工观察或有限事件确认，直接记录在实机结果中。核心操作因协议限制无法完成时，列为交付阻塞。

## 集成顺序

1. 在独立测试页面用候选协议投放一段测试影片，再用两集样片验证换集，记录可用接口及其限制。
2. 将选定协议接入现有播放器数据和控制，完成连接、交接、控制、换集、结束及失败恢复。
3. 用正式的家庭部署地址完成下面的实机验收，并在手机和电脑复查网页播放。

## 实机验收

组合记录填写为「手机型号、系统版本、浏览器版本／电视或盒子型号、系统版本／家庭网络与站点协议／媒体格式／采用的投屏协议」。目前各项等待目标设备及实机结果。

| 验收项 | 通过条件 | 当前状态 |
| --- | --- | --- |
| 设备发现与连接 | 目标家庭网络中能从手机选到指定电视并连接。 | 待实机验证 |
| 播放交接 | 手机从影片中段发起，电视显示正确内容并从对应位置继续，手机停止本地音视频输出。另测暂停状态下发起。 | 待实机验证 |
| 控制与跳转 | 从手机暂停、继续，前后跳转各一次，电视画面或声音确认操作生效。记录手机可显示的进度及必要限制。 | 待实机验证 |
| 换集 | 从当前集切至下一集，例如用样片从第 2 集切至第 3 集。电视播放正确剧集，手机显示相同剧集。 | 待实机验证 |
| 结束 | 从手机结束，电视停止本次播放，手机显示投屏已结束并能继续使用本地播放器。 | 待实机验证 |
| 故障恢复 | 用不可达媒体地址或主动断开测试，手机显示可理解的反馈并能重试或回本地播放。 | 待实机验证 |
| 网页回归 | 用手机和电脑各验证一遍直接播放、暂停、跳转和换集。 | 待实机验证 |
